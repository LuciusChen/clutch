# ER view of a table

`clutch-er-diagram`, `r` in the object actions, shows one hop of relations around a table: its key columns in a box, the tables its foreign keys reference and the tables whose foreign keys reference it, one line for each key. Relations the database does not declare can be added by hand, a wide window draws three connected columns, and the record view follows the same relations.

## Keys stay in one contract

A composite key must be one relation, so the view needs to know which columns form one key. `clutch-db-foreign-keys` returned one entry per column with no key identity. A new generic returning grouped constraints was considered and rejected: it would have put a second query and a second cache entry beside the per-column one, and every consumer of the cache would have had to choose between them. Instead the per-column contract gains `:constraint`, a value the columns of one key share, listed together in the key's order. PostgreSQL reports the constraint name, MySQL the constraint name, and SQLite the key's number in its table. The cache, Follow FK, describe buffers and completion hints are unchanged; a column in two keys has two entries, and per-column readers keep the first, as they did. JDBC does not report `:constraint` yet, and a missing key identity is left missing rather than invented: a JDBC connection refuses the view, since it also has no `clutch-db-referencing-keys`.

Reading the keys again showed three defects, each fixed with its own regression. PostgreSQL joined `information_schema` views by constraint name alone, which crossed the columns of a composite key, mixed in a same-named key of another table, dropped keys into other schemas and hid every key from a user who did not own the referenced tables; the catalogs (`conkey`/`confkey`) have none of these problems. MySQL did not report the referenced database, so Follow FK across databases opened a table of the same name in the current one. SQLite left the referenced column empty for `REFERENCES parent`, which means the parent's primary key, and Follow FK failed on it.

`clutch-db-referencing-keys` is new. Its default refuses with a `user-error` rather than returning nil, since an empty list would claim that nothing references the table. PostgreSQL leaves out the copies of a key that partitions inherit (`conparentid`). SQLite has no index of incoming keys, so it reads the keys of every table in the database; the view states that cost.

## Loading and drawing

The view loads synchronously, as describe does: native PostgreSQL and MySQL metadata already runs on the main thread when idle, so an asynchronous path would have added state without freeing Emacs. It refuses while a statement runs and waits for a background metadata request, as foreground SQL does. Columns and foreign keys come from the schema cache (`clutch--ensure-foreign-keys` is the synchronous twin of the async loader and runs the same update hook); the referencing keys are read each time the view loads, since only the view uses them. The model lives in the view's buffer, which binds the connection like any attached buffer, so `clutch--replace-connection` moves it.

Moving point only moves overlays: each highlightable line records the relations it belongs to, and the post-command hook acts only when that set changes. The buffer is drawn again only for a new table, a column toggle or a refresh.

Drawing uses two pure functions added to `clutch-viz.el`, `clutch-viz-columns` and `clutch-viz-box`. Widths come from `string-width`, and padding is real spaces carrying `(space :align-to COL)`, as the plan chart's is. Alignment is exact in a monospace font whose box and arrow glyphs are one column wide, in a terminal or a graphical frame, CJK names included, which take two columns. `clutch-viz-charset` now checks the extra glyphs a caller draws with (`◆ → ← ↔ …`); when any is two columns wide, as with `cjk-ambiguous-chars-are-wide`, the view draws with ASCII. A terminal whose own width for these glyphs differs from Emacs's cannot be detected. With a proportional font, `:align-to` keeps column starts and the box's right edge in place on graphical frames, but the top edge's run of `─` after a title can still drift, and a cell is not guaranteed to fit its column.

## Relations added by hand

They live in `clutch-er.el` with the view, as plain parsed JSON (alists and vectors) that is read, checked strictly and written back in the same shape, so no second representation has to stay in step with the file. A file with another version, a field Clutch does not know or a malformed relation is refused by name rather than partly read, because writing it back would drop what was not understood. Writing sorts the relations by their encoded text and puts one field on a line, so Git shows a change as the relation it touches; the file is replaced through a temporary file beside it, after following a link. Each change reads the file again first, so a change made in another Emacs or by hand since the view loaded is kept, and editing or deleting a relation that is gone says so.

An end leaves out its schema when it is the connection's current schema, and an end without one means the current schema. One rule for writing and reading keeps a file shared by databases whose schemas differ usable, at the cost that such a relation follows a schema switch. Matching a relation to the shown table or to a key of the database uses the same rule. Names are compared as stored, since both ends come from metadata. A relation that repeats a key of the database is refused when added and hidden when shown, as the database may have gained the key since; comparing the set of column pairs, not their order, is what makes a composite key and its stored twin equal.

The file belongs to a connection: `:relations-file` names it, for a file shared in a project, and otherwise it is named after the backend, URL or profile entry, host, port and database in the connection's parameters. Those are the parameters it was opened with, not the endpoint of an SSH or TRAMP forward, whose local port changes each time, and not the saved connection's name, which the parameters do not carry. `:relations-file` is removed from the parameters a backend receives, with the other Clutch keys.

A result starts a relation at the source column of the column at point, through `clutch-result--writable-source-column`, so an alias names its column and a computed column is refused; it first checks that the result has a connection and that the session still resolves names as the result's query did.

## Wide layout

A window wide enough draws the referencing tables on the left and the referenced tables on the right, so every arrow points the same way, from the table that holds a key to the table it references. A general graph layout was not attempted: one hop has a fixed shape, and a deterministic three-column layout is all it needs. Each relation gets a lane of its own in its gutter, and each gutter cell records the directions it connects as four bits; the character is looked up from them, so crossings and merges need no special case, and `clutch-viz-connectors` stays a pure function of line numbers. A connector joins only the first pair of a composite relation; highlighting its relation shows the rest. Boxes in a column share one width, so every connector starts at a box edge. The lists stay under the boxes in both layouts, so the commands that act on a relation work on the same lines, and the connectors carry the relation ids for highlighting only. The view is drawn after its window is shown, and a change of width redraws it only when the layout it needs changes. Spans to highlight are read back from the `clutch-er-ids` property after drawing, so both layouts share them. Screenshots of a graphical frame found two faults that text tests could not see. `:align-to` counts from the window's left edge, so the padding inside a box placed in the middle or right column collapsed; `clutch-viz-columns` now drops the `display` property of a cell it places right of column 0, keeping its spaces, while the columns themselves stay aligned from column 0. And a highlight drawn as a background vanished next to box characters: in DejaVu Sans Mono and similar fonts they are taller than a line, and the frame redraws the neighbouring lines' background over the highlighted line. `clutch-er-highlight` therefore colors and emboldens the text instead. Inside the wide layout's middle and right boxes alignment rests on the font being monospaced; a CJK font that is not exactly two cells wide can shift those boxes' right edges by a few pixels.

## Following relations from a record

Follow FK names every column of a key, from the row's values in the result, so a composite key opens the one row the record references; a column of the key that the result does not show, or a NULL in it, is refused rather than dropped from the condition. It uses the values the database holds, not staged edits. `RET` takes the first relation through the field, and `r` chooses among the foreign keys and the relations added by hand, which come from `clutch-er-outgoing-relations`, the grouping and deduplication the ER view uses. Without key identity, as over JDBC, each column is a relation of its own rather than being joined to a neighbouring column that references the same table.

## Deferred

- JDBC: the agent's foreign-key operations must report key identity and the keys that reference a table.
- `clutch-db-primary-key-columns` on SQLite lists primary-key columns in table order rather than key order; the view's implicit-reference lookup sorts by key position itself.
