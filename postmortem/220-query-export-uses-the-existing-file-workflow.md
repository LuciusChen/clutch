# Direct query export uses the existing file workflow

## Decision

Issue #121 asks to export SQL from its editing buffer without first opening a result. `M-x clutch-export-query` and Execute → Export query to file (`C-c ?`, then `e`) accept one SELECT, including SELECT-only CTEs, and ask for CSV/TSV, encoding and a file. Normal execution and the result export menu keep their behavior. Export leaves an existing result and staged edits intact, so it does not run the query-preparation step that asks to discard those edits.

The command lives with export in `clutch-result.el`, using the statement boundaries already owned by `clutch-query.el` and the shared SELECT classifier. Its first page supplies columns directly to the existing formatter, and later pages keep that layout because Oracle's pagination adds an RN column after the first page. It does not create a hidden result buffer, run a preview query, or load editing identity metadata. The existing file writer takes a batch producer, with result export as its default. The existing page loop supplies rows and columns to its consumer. This shares asynchronous ownership, the reply gate, cancellation and atomic replacement rather than adding another state machine.

Entry points are limited to the menu and M-x, leaving the execution command unchanged and adding no cross-module declaration.

The wide JDBC fixture exposed a separate completeness bug: Oracle RAW and SQL Server VARBINARY values containing `abc` returned only `(:__type "blob" :length 3)`, which the formatter exported as data and the viewer displayed as 26 bytes of content. The JDBC normalization layer converts length-only BLOBs to `clutch-db-value-preview`, using the reported length and empty text. The shared `clutch-db-require-complete-value` remains unchanged and rejects these previews through the same rule as incomplete CLOBs; the viewer also recognizes the unavailable content and actual length. Complete decoded JSON/XML text remains usable.

## Scope and limits

The shared classifier refuses multiple statements, SELECT INTO and recognized data-changing CTEs. It does not establish that arbitrary functions invoked by a SELECT are free of side effects. Paging repeats the query with the existing backend pagination rules; explicit LIMIT/OFFSET, TOP and FETCH run once. Stable ordering and snapshot consistency remain the same user responsibilities as result export. There is no new cursor, snapshot transaction or retry policy.

CSV/TSV formatting and file writes run on Emacs's main thread. Asynchronous MySQL/PostgreSQL/JDBC statement waits do not make the whole operation background work: JDBC remaining-row fetches and SQLite execution can block, explicit limits may materialize the whole result, and filename transformations such as gzip may hold the complete output in memory. Direct export has elapsed-time feedback and cancellation in its source buffer; it does not add statement fringe markers in this first implementation.

## Verification

Direct interactive command execution against SQLite checks statement boundaries, SELECT-only CTEs, explicit limits, empty headers, CSV/TSV quoting, Unicode, NULL versus empty text, and a single UTF-8 BOM across pages. Controlled asynchronous replies check atomic replacement and cleanup on success, page error, cancellation meeting a reply, killed or moved source buffers, incomplete values and nonlocal writer exits. Native MySQL/PostgreSQL coverage runs the command on a selected SELECT and CTE, verifies that it returns before replacement and produces the expected complete file without a result grid.

The wide live fixture has 101 columns and 602 rows, with 20 field cases repeated across the width: integer sizes, exact decimals beyond double precision, floating point, booleans, dates/times, character/text, Unicode, quotes/newlines, binary converted explicitly to hex, JSON, UUID, NULL and empty text. Each dialect uses its supported types; Oracle's empty text is NULL and its DATE includes midnight. The test checks primary-key metadata and an actual zero index count in the database catalog, then compares every CSV and TSV cell against literal expected text. It uses 200-row export pages and 50-row JDBC fetch batches, covering remaining-row fetches as well as Oracle's added RN column. The width is retained at the maintainer's request: beyond shared formatter tests, it verifies that many columns survive actual driver serialization and JDBC continuation fetches on every page, while direct export works without identity discovery on an index-free table. It does not claim 101 distinct SQL types or benchmark large tables. Oracle CLOBs need storage indexes, so they have a separate fixture: complete short values export, truncated values fail after a previous page was written and leave the destination intact. Separate Oracle/SQL Server fixtures also verify complete XML binary text and refusal of unavailable binary content.

`test/run-ci.sh all` passed on Emacs 29.4, 30.2 and 32.0.50: 703 main tests, 284 backend tests and 13 architecture tests; the sandbox-only container-forward test skipped. Byte compilation, package-lint and checkdoc reported no warnings. The BLOB viewer regression failed on `814491b`, which displayed the metadata as 26 bytes instead of an unavailable 3-byte value; it passes with JDBC normalization. Removing only the length-only BLOB normalization branch makes both the viewer and export-rejection tests fail, checking that they detect the missing behavior.

The complete native/JDBC runner passed 15 suites, with 245 passing tests, 221 backend capability skips and no failures. Live tests used disposable OrbStack PostgreSQL 16, MySQL 8.0, XTDB 2.1, Oracle Free, SQL Server 2022, ClickHouse 24.8, MongoDB 7 and Redis 7 fixtures, plus local DuckDB and the pinned agent 0.2.26 in an isolated runtime. The wide export passed on PostgreSQL, MySQL, Oracle, SQL Server and DuckDB, and the Oracle/SQL Server BLOB tests passed with normalized previews. The previous LZ4 error came from a newer ClickHouse image; this verified matrix pins `CLUTCH_TEST_CLICKHOUSE_IMAGE=clickhouse/clickhouse-server:24.8` and includes ClickHouse UI and backend coverage without a product change. User configuration and installed JDBC artifacts were unchanged.

All owned test containers were removed with their anonymous volumes. Docker's volume set remained exactly the same 26 volumes as before testing; no production connection was used.

A separate disposable PostgreSQL fixture exported 20,000 rows (6,568,902 CSV bytes) with 500-row pages: dispatch returned in 81 ms, completion took 2.08 s, and a 10 ms timer performed 202 edits in another buffer with a maximum measured gap of 80 ms. Cancelling a real `pg_sleep(5)` export after 100 ms completed in 185 ms, preserved the old file, removed the temporary output and released the connection. These measurements demonstrate yielding for this workload, not a guarantee for large cells or slow file handlers.
