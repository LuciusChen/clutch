# Direct query export uses the existing file workflow

## Decision

Issue #121 asks to export SQL from its editing buffer without first opening a result. `C-u C-c C-c` and `clutch-export-query` accept one SELECT, including SELECT-only CTEs, and ask for CSV/TSV, encoding and a file. Normal execution and the result export menu keep their behavior. Export leaves an existing result and staged edits intact, so it does not run the query-preparation step that asks to discard those edits.

The command lives with export in `clutch-result.el`, using the statement boundaries already owned by `clutch-query.el` and the shared SELECT classifier. Its first page supplies columns directly to the existing formatter, and later pages keep that layout because Oracle's pagination adds an RN column after the first page. It does not create a hidden result buffer, run a preview query, or load editing identity metadata. The existing file writer takes a batch producer, with result export as its default. The existing page loop supplies rows and columns to its consumer. This shares asynchronous ownership, the reply gate, cancellation and atomic replacement rather than adding another state machine.

The prefix and menu require one new query-to-result declaration for the public export command; byte compilation needs it on the existing lazy boundary, raising the architecture count from 18 to 19. `clutch.el` remains the autoload entry point. No protocol adapter, agent artifact or installed configuration changes are needed.

The wide JDBC fixture exposed a separate completeness bug: Oracle RAW and SQL Server VARBINARY values containing `abc` returned only `(:__type "blob" :length 3)`, which the formatter exported as data. Both live regressions and a CSV regression failed before the fix. The existing shared `clutch-db-require-complete-value` now refuses such metadata-only values, so result copy/export and mutation paths share the same rule. This does not invent bytes or another transport representation: SQL can explicitly encode a binary column as hex, and already complete decoded JSON/XML text remains usable.

## Scope and limits

The shared classifier refuses multiple statements, SELECT INTO and recognized data-changing CTEs. It does not establish that arbitrary functions invoked by a SELECT are free of side effects. Paging repeats the query with the existing backend pagination rules; explicit LIMIT/OFFSET, TOP and FETCH run once. Stable ordering and snapshot consistency remain the same user responsibilities as result export. There is no new cursor, snapshot transaction or retry policy.

CSV/TSV formatting and file writes run on Emacs's main thread. Asynchronous MySQL/PostgreSQL/JDBC statement waits do not make the whole operation background work: JDBC remaining-row fetches and SQLite execution can block, explicit limits may materialize the whole result, and filename transformations such as gzip may hold the complete output in memory. Direct export has elapsed-time feedback and cancellation in its source buffer; it does not add statement fringe markers in this first implementation.

## Verification

Public prefix execution against SQLite checks statement boundaries, SELECT-only CTEs, explicit limits, empty headers, CSV/TSV quoting, Unicode, NULL versus empty text, and a single UTF-8 BOM across pages. Controlled asynchronous replies check atomic replacement and cleanup on success, page error, cancellation meeting a reply, killed or moved source buffers, incomplete values and nonlocal writer exits. Native MySQL/PostgreSQL coverage runs the public prefix on a selected SELECT and CTE, verifies that it returns before replacement and produces the expected complete file without a result grid.

The wide live fixture has 101 columns and 602 rows, with 20 field cases repeated across the width: integer sizes, exact decimals beyond double precision, floating point, booleans, dates/times, character/text, Unicode, quotes/newlines, binary converted explicitly to hex, JSON, UUID, NULL and empty text. Each dialect uses its supported types; Oracle's empty text is NULL and its DATE includes midnight. The test checks primary-key metadata and an actual zero index count in the database catalog, then compares every CSV and TSV cell against literal expected text. It uses 200-row export pages and 50-row JDBC fetch batches, covering remaining-row fetches as well as Oracle's added RN column. Oracle CLOBs need storage indexes, so they have a separate fixture: complete short values export, truncated values fail after a previous page was written and leave the destination intact. Separate Oracle/SQL Server fixtures also verify complete XML binary text and refusal of unavailable binary content.

`test/run-ci.sh all` passed: 702 main tests, 284 backend tests and 13 architecture tests; the sandbox-only container-forward test skipped. Byte compilation, package-lint and checkdoc reported no warnings. Live tests used disposable OrbStack fixtures and the pinned agent 0.2.26 in an isolated runtime; the installed checkout, configuration and JDBC artifacts were untouched. The wide export passed on PostgreSQL 16, MySQL 8.0, Oracle Free, SQL Server 2022 and DuckDB. UI suites passed 50, 44, 20, 18 and 20 tests respectively, with backend capability skips; XTDB 2.1 passed 12 tests. Backend suites passed PostgreSQL 12, MySQL 12, cross-backend 2, MongoDB 7 10, Redis 7 6, Oracle 17 and SQL Server 8 tests.

The full native/JDBC runner stopped at ClickHouse: eight existing UI tests failed with `Invalid LZ4 magic byte: '-112'` or their consequent missing results. The unchanged base main (`9be1b33`) reproduced the same compression error in `clutch-test-live-paged-sql-building`, using the same ClickHouse fixture and bundled driver 0.9.8. DuckDB and the backend suites listed above were then run separately using the original runner's functions; ClickHouse backend coverage did not run. This is not a fully green combined matrix, and no unrelated ClickHouse change is included. An earlier stopped SQL Server test container was removed and recreated after exiting with code 139; its UI and backend suites passed on the new fixture. The DuckDB wide fixture initially called COMMIT in auto-commit mode and failed because no transaction was active; removing the fixture's unnecessary COMMIT calls made it pass without a product change.

All owned test containers were removed with their anonymous volumes. Docker's volume set remained exactly the same 26 volumes as before testing; no production connection was used.

A separate disposable PostgreSQL fixture exported 20,000 rows (6,568,902 CSV bytes) with 500-row pages: dispatch returned in 81 ms, completion took 2.08 s, and a 10 ms timer performed 202 edits in another buffer with a maximum measured gap of 80 ms. Cancelling a real `pg_sleep(5)` export after 100 ms completed in 185 ms, preserved the old file, removed the temporary output and released the connection. These measurements demonstrate yielding for this workload, not a guarantee for large cells or slow file handlers.
