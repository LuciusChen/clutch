# Statement plan tree

`clutch-explain-plan`, `E` in the console menu, shows a statement's plan as a tree of steps in `*clutch-plan*`. Two generics carry it: `clutch-db-plan-sql` returns the SQL that asks for a plan, or nil when the connection has none, and `clutch-db-plan` reads that SQL's result into nodes of `:label`, `:total`, `:rows` and `:children`. Splitting them lets the plan SQL run through `clutch-result--run-query` like any other statement, so it does not block Emacs, can be cancelled, and reports a failure where statements do; the alternative, one generic that runs the query itself, would have meant a synchronous call on the connection outside the query activity.

PostgreSQL asks for `EXPLAIN (FORMAT JSON)`, which pgsql.el already decodes into hash tables, and labels a step the way text EXPLAIN does (`Hash Left Join`, `Index Scan using a_pkey on a x`). SQLite's `EXPLAIN QUERY PLAN` rows link each step to its parent by id, which becomes the tree; it has no measure and cannot measure a plan. MySQL asks for its tree format, `EXPLAIN FORMAT=TREE` or `EXPLAIN ANALYZE`, one text row whose steps are `->` lines indented four spaces per level; `FORMAT=JSON` was rejected because its shape changes between versions while the tree text has stayed stable since 8.0.16. The cost may be written as a `STARTUP..TOTAL` range on newer servers, and a step that never ran under ANALYZE counts zero time and unknown rows rather than its estimate, so estimates never mix with measurements. MariaDB has no tree format and opts out by its server version, as XTDB, a PostgreSQL connection without a JSON plan, does. Both readers live in `clutch-backend.el`, since adapters require only the backend, and the JDBC adapter uses them when the connection's URL starts with `jdbc:postgresql:` or `jdbc:mysql:`; the PostgreSQL reader accepts the JSON as the text JDBC returns or as pgsql.el's decoded value. The URL, not the server, decides, so a `jdbc:mysql:` URL to a MariaDB server fails with its syntax error instead of being refused. Other JDBC databases are left for later, since each has its own plan syntax: Oracle writes a plan table before `DBMS_XPLAN` reads it, and SQL Server's `SHOWPLAN_XML` changes the session so that statements stop running.

A step's bar is its own share: its total less its children's totals, since PostgreSQL's cost and time both include the children, and an inclusive bar would always point at the root. A measured time is the per-loop average times the loops. PostgreSQL reports a parallel step's time per worker, so shares under a `Gather` are approximate; Init Plans and Sub Plans are children like any other.

`C-u` measures the plan with `EXPLAIN ANALYZE`, which runs the statement. It is refused unless the statement is one SELECT that does not write, by the same `clutch-db-sql-pageable-query-p` check export uses, so a measured plan never deletes or updates rows. `g` in the plan buffer redraws the plan it holds at the window's width and never runs SQL again.

Drawing lives in `clutch-viz.el`, pure functions over Lisp data with no Clutch dependency, which the architecture check enforces with an empty allowlist. The bar follows glyph-kit's algorithm (eighths of a cell, a positive value never drawn empty), but glyph-kit itself is not used: its CLI needs Node, caps a figure at 16 rows and 80 columns, and measures width with a fixed table in which box and block characters are always one cell. In a CJK language environment with `cjk-ambiguous-chars-are-wide`, `█`, `─` and `…` become two columns in Emacs (checked on Emacs 32), so `clutch-viz-charset` falls back to ASCII whenever a block or box character is not one column. Padding is real spaces, so copied text stays aligned, carrying a `(space :align-to COL)` display property, so a graphical frame aligns even when a glyph is not an exact multiple of the default width. A bar chart of a result column, `B` in the result buffer, was built on the same functions and dropped: it covered only the loaded page, which a `GROUP BY` answers better.
