# Native isearch reaches result headers

Result column names previously existed only in `header-line-format`, outside searchable buffer text. ETAF's useful precedent is a real buffer header plus a fixed copy: native isearch reaches the real text, rather than searching the displayed header-line string. Reuse this arrangement without bringing in ETAF or adding a window. The earlier overlay-only experiment is a separate branch and is not part of this implementation.

The first version kept the real first row in the buffer whenever `clutch-result-searchable-header-mode` was on. That made every other command meet it: selecting the whole buffer started the region in the header, so copy and aggregate failed with "No cell at region start"; clamping the start lost its column, and point could rest where no cell exists. The header now exists only for the duration of a native search. An advice before `isearch-mode` inserts the row built by the existing header renderer, and an advice after `isearch-done` removes it unless the search is only suspended to edit its string. `isearch-mode-end-hook` was the first choice and was wrong twice: `M-e` runs it too, so the header vanished and was reinserted around the minibuffer and the re-entered search failed where it had succeeded, and `isearch-done` pushes the mark from its integer `isearch-opoint` after the hook, which put the mark a header length past the starting cell. Inserting before the search starts keeps isearch's recorded positions consistent, so `C-g` returns to the starting cell and the buffer text afterwards equals the text before. Ending the search on a header leaves point on the same column's first data cell. Data rows keep their own row/cell properties; the header carries column identity only. Truncated column names keep their complete raw text with the fitted label as a display replacement, so native isearch matches the complete name while cell width is preserved. No search advice beyond that insertion, remapped command, duplicate search index or synthetic data row is needed.

Window-local header-line parameters suppress the fixed copy while that window's point is in the real header. Returning to data, switching buffers, disabling the mode and killing the result restore the window's previous setting. Search follows ordinary buffer order: backward search reaches headers from data, forward search reaches them after wrapping, and matching data values remain ordinary matches.

Keep the header's mouse keymap but omit its header-line-only `local-map` replacement in buffer text: carrying that property into the buffer hid the result's normal keyboard bindings. Moving between header columns during a search only moves the active-column face on the real header, and rebuilds the fixed header only once point is back in data. Rebuilding both on every match cost about 100 ms per `C-s` on a 150-column result, and discarded the fixed header's hscroll crop cache.

When the fixed copy is hidden it cannot run its usual font-metric check, so a buffer-local post-command hook and `text-scale-mode-hook` schedule the existing metric refresh while point is in the real header. The check must not run from `pre-redisplay-functions`: on macOS GUI Emacs `string-pixel-width` measures against the window's glyph matrix, and doing so while the real header occupies the first text row interferes with cursor drawing, leaving the cursor zero pixels wide after the blink turns it off.

Hiding the header line while the viewport is far below the header made the next redisplay scroll back to the top very slowly. On `zj_test`'s `ffp_invoice_application_batch` (768 rows, 45 columns) the first redisplay after a search wrapped into the header took 12-17 seconds, later ones about two, while the same jump with the fixed header line kept took 30 ms. Neither the header's text properties, bidi reordering nor the number of window parameter writes mattered; setting the window start to `point-min` before redisplay brought it to 13 ms. The redisplay itself ran inside `isearch-lazy-highlight-new-loop`, so the time showed up in the `C-s` command rather than in any Clutch function. Synthetic wide results with short lines did not show it, so wide-result checks for redisplay work need real data.

The feature remains opt-in. It does not replace the default header-line renderer or make only headers searchable. Enabling the mode in a result lasts until the major mode is initialized again, which every query does; `clutch-result-searchable-header` enables it in each subsequent result. Other search commands see the header only if they go through isearch. Backend protocol, query and export paths are unchanged.

Validation covered Emacs 29.4/30.2/32.0.50 for the non-live gate, and Emacs 32 GUI for search timing: a 150-column, 500-row result and the `zj_test` table above, with isearch lazy counting on. Timing the commands needs explicit calls around `redisplay`, since the profiler returns no samples on this build.
